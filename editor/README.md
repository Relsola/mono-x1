# 关卡编辑器（editor）

用 Dear ImGui 写的最小可用关卡编辑器。**独立程序**：产物是 `build\editor.exe`，
和游戏的 `build\main.exe` 互不影响（不共享进程、不共享渲染器、不共享 GameState）。

它只做一件事：**编辑 `data/map/*.bin` 这一层编辑语义**（tile、地刺、门、移动组件、怪物），
也就是 `include/shared/level_asset.h` 定义的那份数据。运行期的东西（`Platform` 碰撞体、`GameState`、相机、
渲染）它一概不认识 —— 那是游戏加载后才产生的。

## 构建与运行

```bat
editor\build.bat             :: 可以从任何目录跑，脚本自己 cd 到仓库根
build\editor.exe             :: 从**仓库根**启动（路径按进程工作目录解析，和游戏一样）
build\editor.exe data\map\second.bin    :: 也可以指定关卡
```

不带参数时打开 `data/map/first.bin`；打不开就新建一个空模板（模板自带地面与出生点，直接能通过校验）。

## 界面

```
┌ 文件  编辑  视图  帮助 ─────────────────────────── 当前文件 *未保存 ┐
│ 物件（笔刷 / 实体） │ 网格（画布）             │ 属性 / 检查          │
│  · 地形笔刷 4 种    │  · 格子、实体、门、出生点 │  · 关卡属性（单例）  │
│  · 实体列表 + 新建   │  · 合并碰撞体叠加层       │  · 选中物的参数      │
│  · 消息区           │  · 诊断高亮               │  · 校验问题 + 诊断   │
└ 路径 | 版本 | 尺寸 | 光标格 | 实体数量 | 出生点 | 改关卡的后果 ─────┘
```

快捷键：

| 操作 | 键 |
| --- | --- |
| 涂当前笔刷 / 擦成空 | 左键拖动 / 右键拖动 |
| 选中光标下的物件 | **Ctrl + 左键**（从小的往大的找：出生点 → 怪物 → 平台 → 地刺） |
| **拖动选中的物件** | 选中后：**拖它内部 = 平移**（附属位置点跟着走）、**拖边/角的小白块 = 缩放** |
| 自由像素（不按格吸附） | 拖动时按住 `Alt` |
| 取消选中 | `Esc`（选中期间不能在它内部涂格子，取消后就能） |
| 平移 / 缩放 | 中键拖动 / 滚轮（以鼠标为中心） |
| 切换笔刷 | `1` 实体墙、`2` 单向平台、`3` 出生点、`4` 空、`5` 地刺 |
| 删除选中的物件 | `Delete` |
| 保存 | `Ctrl + S` |
| 撤销 / 重做 | `Ctrl + Z` / `Ctrl + Y`（也接受 `Ctrl + Shift + Z`） |
| 切换网格 / 碰撞体叠加 | `G` / `C` |
| 回到整幅关卡 | 视图 → 全览 |

拖动的规则：**左键按在已选中实体的手柄/内部才算拖动，其它情况还是涂格子**。
所以「选中」是拖动的入口（Ctrl+左键 或在左栏列表里点一下）。吸附默认一栅（`tile_size`），
按住 `Alt` 自由像素；吸附作用在**结果**上而不是增量上，所以拖多少个来回都不会漂。

可拖的附属点（都只在选中时显示手柄）：

- 怪物的**复位点**（白圆圈）——单独拖它只改 `spawn_x/spawn_y`，拖身体会把复位点一起带走
- 移动组件的**往返轴端点**（两个扶手：方块 = A、菱形 = B）——单独拖改 `point_a` / `point_b`（二维，
  所以轴可以竖着放、斜着放），**本体按定义就在轴上**：端点一转，它就按同一个 `t0` 跟过去。
  拖本体 = 两端一起平移（t0 不变）；拖边手柄 = 只改尺寸（中心由 t0 决定，不会跟着跑）
- **出生点**（格子底边那个黄色标记）——它只能落在格子里

## y 轴怎么显示（默认「底部为 0」）

编辑器里显示的、填的、拖的 y 都是**屏幕习惯**的那种：关卡底部 = 0，往上变大
（所以「顶部 = 关卡高」，`first.bin` 就是 `0 ~ 1536`）。顶部为 0、向下为负的**原始世界 y**
只存在于关卡数据、游戏与机器可读产物里。两者只差一个平移：`显示 y = 世界 y + 关卡高`（没有缩放）。

- 视图菜单 → 「Y 轴：底部为 0（向上为正）」取消勾选就切回原始世界 y；状态栏会标出当前用的是哪种。
- **为什么留这个开关**：`--trace` 的 CSV、`test/*.txt` 里的 `assert_pos`、日志、`docs/` 里的常数
  （如「地面顶面 -1408」）用的都是原始世界 y。要拿编辑器里的数字去对它们，就得切回去。
- 换显示方式**不会改动关卡数据的任何一个字节**（画布、命中测试、拖动、存盘一律是世界 y），
  所以它与存盘结果、与 `test\run_tests.bat` 的确定性对拍都无关。

## 三类"物件"的划分（这是编辑器的核心判断）

| 层 | 例子 | 数据形态 | 界面 |
| --- | --- | --- | --- |
| **格子值** | 墙 `#`、单向 `=`、空 `.`、地刺 `^`、可消失平台 `V` | `LevelAsset.tiles` 里的一个 `u8`，**无身份** | 笔刷 + 拖动 |
| **关卡单例属性** | 出生点 `P` | 也是 tile，但约束是「全图唯一」 | 右栏「关卡属性」段；涂第二个会自动搬走第一个 |
| **实体** | 门、移动组件、怪物、传送门、传送点 | 结构体数组项，**有身份**（种类与字段位置在共享注册表里） | 左栏列表 + 右栏参数 + 画布上拖 |

判据只有一句：**它需要被单独选中 / 改参数 / 删除吗？** 需要就是实体（进数组），不需要就是格子值。

## 编辑逻辑单独一层：`editor_edit`

命中测试、拖动判定与解算、吸附这些**规则**住在 `src/editor_edit.h/.cc`，是**纯函数**：

- 入参是 `LevelAsset *` + 一个 `EditorPointer`（世界坐标 + 两个由「像素 ÷ zoom」换算出来的半径）+ 拖动状态，
  出参是结构体。**不碰窗口、不碰 ImGui、不读全局** —— 所以能在无窗口下被直接调用、被自检。
- UI 层（`editor_ui.cc`）只剩三件事：屏幕坐标 → 世界坐标、把参数递进去、把结果画出来。
  于是「拖不动 / 拖错东西 / 吸附漂了」这类问题能在 `--selftest` 里定位，而不是只能靠手点。
- 判据是**同一份规则只能有一处**：以前手柄命中、内部命中与拖动解算混在绘图代码中间，
  同一个半径要在命中与光标形状两处各写一遍（漂了也不报错）。

`--selftest` 就是这一层的用例集（见下）。

## 撤销 / 重做（定长快照环）

`Ctrl+Z` / `Ctrl+Y`，或菜单「编辑 → 撤销 / 重做」。上限 **128 步**（含重做）。

- **形态是快照**：每格存一份「第 k 次改动之后的文档」（tiles + 实体数组，约 1.7KB），
  当前状态就是游标那格 —— 撤销 = 游标往回一格并把内容写回，重做 = 走回来。
  不做命令对象 / 增量 diff：文档小、操作简单时快照更便宜，也没有「逆操作写错了」这个错误来源。
- **一次连续操作 = 一步**：画布上按住拖动（拖一格还是拖一千帧都一样）、属性面板里按住一个
  `DragFloat` 拖，都只落一格历史。实现是 `editor_doc_action_begin/end` 包住手势 ——
  **加新的连续交互时必须包**，否则一次拖动会灌进几百格历史。
- **内容没变就不落格**：落格前拿 `level_asset_equal` 与当前格比一次。所以「打开菜单又关掉」
  「输入框里改了又改回去」不留痕迹，也不会平白截断重做尾巴。
- **`*未保存` 是推导出来的**：拿当前内容与「上次打开/保存的那一份」逐字段比 ——
  撤销回到保存点会自己变干净（工业上叫 clean state）。
- 撤销/重做**不自动重跑诊断**：诊断是按钮触发、每次都会分配（见下），撤销几百次会白吃掉 arena；
  右上角照旧显示「结果已过期」。
- 选择里的编号越界（实体被撤销掉又加回来）由文档层顺手夹掉，界面不用自己防。
- 内存：129 格 + 1 格基准 ≈ 700KB，**一次分配、之后永不分配**（arena 不能 free）。
  实体种类多到超出每格预留容量时会重建整个环（历史作废，但撤销仍可用；`editor.log` 里有 WARN，
  不是静默降级）。
- 撤销**只管文档**：视图缩放、笔刷、选中、Y 轴显示方式都不进历史。

## 加一种实体只改两处：共享注册表 + 属性面板

实体那层是一个**注册表**（`include/shared/level_asset.h` 的 `LEVEL_ASSET_ENTITY_TABLE`），
一行描述一种实体：中文名（界面与校验消息共用）、数组与数量在 `LevelAsset` 里的偏移、
元素大小、矩形在元素内的偏移（门没有）、数量上限。游戏与编辑器**共用这一份**。

于是这些地方都不再需要各自的 `switch`：命中测试、列表显示、构建/销毁实体数组、
矩形的通用检查（有限值/非退化/越界）、出生点重叠检查、数量上限检查 —— 全是表驱动。

> 加一种实体 = 注册表加一行 + 属性面板加一个 `case`（拖动手柄是自动的）。
> 不注册的后果不再是「静默失效」：漏一行就是少了那种实体本身。

判据：**运行字段不同的东西不强行统一**。游戏的运行时（`Level`/`GameState`）仍然按类型写字段与初始化 ——
那张表服务的是「编辑语义」这一层。

两个运行时硬约束（编辑器必须拦住，否则游戏直接 abort）：

- 移动组件最多 8 个（`LEVEL_ASSET_MAX_MOVERS`）、怪物最多 1 个（`LEVEL_ASSET_MAX_MONSTERS`）
- 出生点**恰好 1 个** —— `LEVEL_ASSET_REQUIRED_SPAWN_TILES`（多个时 `level.cc` 是「最后一个赢」，静默）

这些常数在 `include/shared/level_asset.h`，**游戏侧的 assert 引用的是同一个数字**。

## 校验与诊断（两件不同的事）

**校验**（右栏实时，每帧跑）＝ 纯 `LevelAsset` 的语义检查，零分配、不编译：

- 规则表与判据写在 `include/shared/level_asset.h` 的 `LevelAssetIssueKind`；
  实现是共享层的 `level_asset_validate()`（`src/shared/level_asset.cc`），
  **编辑器与游戏侧引用同一批常量**，规则只有一份。
- `ERROR` 级问题**会拒绝保存**；`WARN` 只提示。两者都带中文说明，能定位的（带格坐标）可以点「定位」跳过去。
- 为什么放共享层：这些规则本质是「游戏侧假设的镜像」（`game.cc` 的 assert）。放两份必然漂移 ——
  本工程在手柄按钮映射上踩过同一个坑（一表一实现、漏改静默失效）。

**诊断**（右栏「检查」按钮触发）＝ 需要**编译**才能得到的信息：

- 点一次会跑 `level_build_from_asset`（tile → 合并碰撞体）并建一张「格 → 碰撞体」反查表，
  然后输出关卡概况、光标格属于哪一块合并体、有哪些实体压在这一格、选中物的派生量。
- **为什么做成按钮**：每次检查约 7KB（编译产物）+ `列×行×4`（反查表），都从 arena 走（只增不减）。
  按按钮触发才有界 —— 不是每帧、也不是每次改动。文档改过之后面板会显示「结果已过期」，
  画布上的「合并碰撞体叠加层」在过期时**不画**（不拿旧数据冒充真相）。
- **校验不过就不编译**：这一部分跑的是游戏自己的 `level_build_from_asset`（`src/level.cc`），
  而它是按「那些规则已经成立」写的 —— 文件里那一串 assert 就是那些规则。
  拿一张有 ERROR 的图去编译会当场 assert（实测：画两个出生点再点「检查」→ 调试构建弹断言框、
  命令行下 `abort`（退出码 3））。所以诊断入口先跑一次与保存同一份的校验，有 ERROR 就只回报「不编译 + 原因」，
  不把非法资产送进编译器。

## 保存路径为什么是安全的

`level_asset_save()`（共享层，`src/shared/level_asset.cc`）做三步：

1. 写 `<路径>.tmp`（**原文件全程不动**）；
2. 立刻 `level_asset_load` 读回来并**逐字段比对**（写错一个字段就当场失败，且这仍是个合法文件 —— 所以要逐字段比）；
3. 通过后才 `file_move_replace` 覆盖原文件。任何一步失败都删掉临时文件、返回 false。

调用方（编辑器）在调用前先跑一次 `level_asset_validate`，有 ERROR 就根本不写盘。

> 改关卡会让旧存档与 `test/baseline.txt` 的断言失效（关卡指纹不匹配会拒载存档，这是设计）。
> 状态栏常驻提示这一点。

## 改完怎么验证：一键把主程序拉起来

两个菜单项（文件菜单里），都会**先保存**（有 ERROR 就拒绝保存，也就不会让主程序去撞）：

| 菜单项 | 干什么 |
| --- | --- |
| 保存并试玩 | 起 `build\main.exe`，不等待 —— 进去手动玩一遍 |
| 保存并冒烟验证 | 起 `build\main.exe --fast input_script test\smoke.txt`，**等它跑完**并把退出码写进消息区 |

冒烟用例（`test/smoke.txt`）刻意**不依赖具体坐标与几何**：它只断言「出生点站得住」（`assert_grounded 1`），
然后走两步、跳一下。所以**改了关卡之后它仍然应该通过** —— 它回答的是「这张图主程序能不能真的加载并跑起来」，
而不是「这张图好不好玩」。退出码 0 = 通过；失败时 `game.log` 里有 FAIL 行。

**失败原因刻意不搬进界面**（2026-09-22 定）：消息区只给退出码 + 「看 `game.log`」的指路，
分析统一在日志里做 —— 那里有脚本文本行号、`context:` 状态行与 `TAPE:` 清单
（形状见 `docs/input-script.md` 第 9 节）。简单场景下把几行细节贴在界面上确实更顺手，
但关卡一复杂，真正有用的分析是跳出来在日志里做的（跨用例、跨运行对比）；
所以不做二层摘要 —— 同一件事在两个地方各说一半，比只在一个地方说清更贵。

需要「一个文件就说完整」时用无头的 `--check --smoke`：它的报告会自动摘录 `game.log` 的失败行
（那条路径是给脚本与 AI 的，见上一节）。

它也已经进了常驻回归：`editor\test\run_tests.bat` 会跑它
（`test/smoke.txt` 本身仍在游戏的用例集里，`test\run_tests.bat all fast` 也会跑到）。

**不是热重载**：游戏启动时读一次 `.bin`，改完必须重起。做热重载要额外处理两件事：
arena 只增不减（每次重载都涨）、以及关卡指纹一变旧存档/旧磁带全部失效（那是设计，不是 bug）。

## 无界面自检：`--check`（给自动化与 AI 的入口）

```
build\editor.exe --check                     检查 data/map/ 下全部 .bin
build\editor.exe --check data\map\first.bin  只查一张（路径后面还能跟 --smoke）
build\editor.exe --check --smoke             检查完再让主程序跑一遍冒烟用例
build\editor.exe --check --out <报告.txt>    换一个报告路径（默认 build/editor_check.txt）
```

- **不建窗口、不初始化 D3D/ImGui**，所以它能在没有显示器/没有焦点的环境里跑。
- 退出码：0 = 每张图都是 0 个 ERROR（且请求的冒烟通过）；1 = 有加载/校验失败或冒烟失败。
- 报告是一份 UTF-8 文本（默认 `build/editor_check.txt`）：每张图给出 `map:` / `entities:` / `validate:`
  （逐条列出 ERROR/WARN）/ `diagnostics:`（与「检查」面板逐字相同的那些行）/ `RESULT:`。
  有父控制台时会顺手回显一份 —— 但**报告文件才是唯一的真相来源**（GUI 子系统进程与控制台的
  交付顺序不可靠，AGENTS 4.5 记过），脚本/AI 一律读文件。
- 冒烟失败时报告会自动附上 `game.log` 里那几行失败信息（FAIL / TAPE: / ERROR），
  所以一个文件就能回答「图好不好 + 游戏为什么不接受它」。
- `--smoke` 跑的是 `test/smoke.txt`，而游戏固定从第一世界出发 —— 所以它只回答
  `data/map/first.bin` 能不能跑（报告里写明了这一点）。

它覆盖的是**资产 + 编译层**。UI 交互（拖动、点 `x`、菜单）它验不了，而 UI 自动化测试本工程**不做**
（理由见下面「明确不做」）。其中「规则」那一半另有一条无窗口入口：`--selftest`（见下节）；
剩下「屏幕坐标 → 世界坐标」那一层只有真开窗点一次才能验。

## 无窗口自检：`--selftest`

```
build\editor.exe --selftest     跑编辑逻辑（editor_edit）的用例集，不开窗口、不读盘
```

它造一份内存里的资产，按「按下 → 拖动 → 松手」的次序调用纯函数，逐条检查判定种类与结果矩形：
世界→格换算、吸附与自由像素、平移、缩放与最小尺寸夹取、命中身体/手柄/端点、复位点跟随平移、端点不越过主体、拖空处不拖。
另有一组**文档层用例**（住在 `editor_doc.cc`）：涂格 / 改字段 / 增删实体的撤销与重做、手势合并、
「内容没变不落格」、撤销后的新动作截断重做尾巴、环满后最旧的那一步被挤掉、选择越界被夹掉。
退出码 0 = 全过；失败时 `editor.log` 里有 `[selftest] FAILED <用例名>` 与期望/实际值。

它**不替代**手点一遍：屏幕坐标 → 世界坐标那条接线（`editor_ui_pointer`）在它的视野之外。
所以动了画布交互后仍要开一次窗、拖一格、`Ctrl+S`，再读 `.bin` 里的矩形字段核对
（用数字而不是截图，做法见 `AGENTS.md` 第 5 节）。这一层的回归由下面那条命令负责。

## 一条命令跑完编辑器自检：`editor\test\run_tests.bat`

```bat
editor\test\run_tests.bat        :: 无参数；从任何目录都能跑（脚本自己 cd 到仓库根）
```

它依次跑两个无窗口入口，都靠退出码判断：

| 步骤 | 命令 | 退出码 0 的含义 |
| --- | --- | --- |
| 交互 / 撤销 / 资产往返用例 | `build\editor.exe --selftest` | 12 条交互 + 8 条文档用例全过 |
| 资产 + 校验 + 编译，再冒烟 | `build\editor.exe --check --smoke` | 每张图 0 error，且主程序跑通 `test/smoke.txt` |

失败时脚本会把关键行打出来（`editor.log` 里的 `[selftest] FAILED`、`build\editor_check.txt` 里的 `RESULT:` / `[ERROR]`），
产物文件留在原地；最后一行是 `==== editor checks: N passed, M failed ====`。
VS Code 里也有对应任务：`editor-test`（= 这条脚本，会先跑 `editor-build`）；
游戏那对是 `build` / `test`。
它**不构建**（先跑 `build.bat` 与 `editor\build.bat`），也**不覆盖「屏幕坐标 → 世界坐标」那一层** ——
那只有开窗点一次才能验。

> **别搞混两个回归入口**：游戏的用例与 runner 在 `test\`（`run_tests.bat` + `*.txt` 用例文件）；
> 编辑器的 runner 在 `editor\test\`，而**编辑器的用例不在 `.txt` 里** —— 它们编进 `build\editor.exe`（`--selftest`）。
> 改编辑器跑前者，改玩法/关卡跑后者；两边都改就两个都跑。共享层（`level_asset.cc` 等）改动属于两边都改。

## 日志：`editor.log`

编辑器用**与游戏同一个** `src/shared/logger.cc`（同一套级别、同一套格式、同一份实现），
但通过 `log_init(path)` 写**自己的文件** `editor.log`（进程工作目录下）。

- 为什么不共用一个文件：游戏每次启动都会清空日志，而编辑器随时会起游戏（冒烟验证）——
  共用的话编辑器刚写的记录会被子进程顺手抹掉（实测踩到过）。
- 记什么：启动/初始化（DPI 缩放）、打开与保存（尺寸与实体数、字节量级、校验结果）、
  增删实体、出生点移动、整片填充/清空、诊断编译结果、每次起游戏的命令行与退出码。
- **不记**逐格涂改（一次拖动几百次调用）与任何逐帧状态 —— 日志的价值在于「哪个人动作导致了什么结果」。
- 级别语义与游戏完全一致：**`LOG_INFO` 走内存缓冲**，正常退出（关窗口）时落盘；
  `LOG_WARN` / `LOG_ERROR` 立即落盘。所以**进程被强杀时最后几行 INFO 会丢**（同 AGENTS 里那条「空日志 ≠ 崩在早期」）。

## 目录与文件清单

```
editor/
  build.bat          自己的构建脚本（**纯 ASCII**：cmd 按本机代码页读 .bat，UTF-8 中文注释会被当成命令）
  README.md          本文件
  include/               编辑器自己的头（不进任何清单，靠 `/Ieditor/include`）
    editor_doc.h         文档层接口 + 选择模型 + 撤销环结构 + 诊断结构 + `--check` / 自检入口
    editor_edit.h        编辑逻辑接口（指针/拖动状态/命中与解算入口）
    editor_ui.h          界面状态（视图/选择/拖动/消息/诊断）
  src/              只有 .cc；头一律在 include/（与游戏那边一样：`include/` 放头、`src/` 放实现）
    editor_main.cc       宿主：Win32 窗口 + D3D11 设备/交换链 + ImGui 初始化 + 主循环
    editor_doc.cc        文档层：打开/保存/校验/增删改/**撤销**/诊断（界面唯一的改动入口）
    editor_edit.cc       编辑逻辑（纯函数）：命中测试 / 拖动判定与解算 / 吸附 / 自检用例集
    editor_ui.cc         界面层：三栏 + 菜单 + 状态栏（改数据走 editor_doc_*，算几何走 editor_edit_*）
  test/run_tests.bat  一条命令跑完 `--selftest` + `--check --smoke`（无参数，从任何目录都能跑）
```

与游戏**共享编译**的源（同一批文件编第二遍，没有静态库）：

```
src/shared/level_asset.cc  格式：reader + writer + 语义校验（头在 `include/shared/level_asset.h`）
src/level.cc           level_build_from_asset（诊断要用编译结果；含 tile → 碰撞体/地刺矩形）
```

**不链**：`game.cc` / `main.cc` / `scene.cc` / `d3d12_renderer.cc` / audio / input / tape / replay / save / trace / debug_vis。

> 还要同步 `compile_commands.json`（四条编辑器条目，否则 clangd 对编辑器代码没有提示）。
> `.clangd` 里已加 `/Ithird_party/imgui` 与 `/Ithird_party/backends`（它不列文件）。

  所有改动本来就汇聚在 `editor_doc_touch` 一个出口上，接上去就行。
- **拖动时多选 / 旋转 / 对齐辅助线**：现在一次只拖一个对象、没有吸附到其他对象。
- 多标签 / 多关卡管理、关卡尺寸与 tile 尺寸的编辑（格式变更）、
  「游戏同款画面」的预览（要处理两个 D3D 设备或改 `renderer_create` 的接口，另说）。
- 在画布里拖**门**：门的位置是「哪一侧边缘」，`entry_x/y` 是**目标关卡**的坐标系 ——
  在画布上拖它会指向一个看不见的地方，所以只能在属性面板里改。

- **UI 自动化测试**：不做常驻测试。理由：唯一能自动碰 UI 的手段是鼠标/键盘注入 + 像素差分，
  它与 DPI、字体、窗口尺寸、ImGui 版本都强耦合，维护成本高于它能挡住的 bug。
  需要验证一次时临时搭探针就够（手法记在 `AGENTS.md` 4.5：只截按钮所在那一栏 + 比较悬停前后的帧差框）。
  编辑器真正的验证走两条路：`--check`（资产/编译层）与冒烟验证（玩法层靠主程序回答）。
- **把 `game.log` 的失败行搬进消息区**：不做（理由见上一节）—— 窗口路径只做「指路」，
  失败原因统一在 `game.log` 里看；要机器可读的单一文件就用 `--check --smoke` 的报告。

## 已知限制

- **DPI**：进程和游戏一样声明 per-monitor-v2 感知，并按系统 DPI 缩放初始窗口与界面
  （`ui_scale` 取自 `GetDpiScaleForHwnd`）。**没做的是运行期 DPI 变化**：把窗口拖到另一个缩放比例的
  显示器上不会重新布局（需要处理 `WM_DPICHANGED` 并重建字体）。
- 中文字体是从 `C:\Windows\Fonts` 里找的（微软雅黑 / 黑体 / 宋体）。都找不到时退回 ImGui 自带字体，
  界面上的中文会变成 `?`（会在消息区说明）。
- 结构性改动（增删实体）会重新分配数组（arena 只增不减），量级几百字节，属用户动作。
- 实体列表那一行是「整行宽的可选中项 + 行尾一个 `x` 按钮」。ImGui 里这种叠加必须先
  `SetNextItemAllowOverlap()`，否则 `Selectable` 会把点击全吃掉、`x` 永远点不到（实测踩过）。

## 下次重构的触发条件（不是现在做）

属性面板现在是**手写的三个 helper**（`editor_field_f32` / `editor_field_rect` / `editor_field_enum`），
加一个字段就是加一行控件 —— 在「4 种实体、每种 ≤6 个字段」这个规模上这是最省的。

**当控件的复杂度开始让每次加属性都很贵时**（信号：出现一组字段在每个实体里重复三遍、
或需要按类型/条件动态决定显示哪些控件、或实体种类 > 8），再考虑做成字段描述表
（`{name, kind, offsetof, min, max, hint}` —— POD 结构体可以这样，不用模板、不违反风格约束）。
到时候按那时的代码与设计重新评估，**不要**现在提前抽象。
