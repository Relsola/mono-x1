## 1. 现象：一句话说清它长什么样

**画面静止时一切正常；一旦相机（或整幅画面）以小于一个像素的幅度慢慢平移，画面里 1 像素宽的东西——细线、描边、砖缝、像素画的暗部边缘——就开始在相邻两格之间来回跳，像整幅画在轻微颤动。**

典型触发场景：

- 平滑跟随相机的"最后一小段"（速度趋近 0，每帧只挪零点几像素）；
- 分辨率越高越容易看见：4K 上"1 像素"的绝对尺寸很小，但它的明暗对比没有任何衰减；
- 线条越细越明显：整条线只有 1 像素宽，跳一格就是 100% 的亮暗变化，而大色块完全看不出来。

我们工程里复现过的具体形态见 `docs/camera.md` §4.1（相机跟随收敛尾段、4K + 细线）。

## 2. 术语表

这一个现象在不同社区有好几个名字，互相之间略有侧重：

| 名字 | 谁在用 | 侧重 |
| --- | --- | --- |
| pixel shimmer（像素闪烁） | 通用 | 现象本身：像素亮度在做高频跳动 |
| texel crawl（纹素爬行） | 3D/引擎 | 表面的纹素图案贴着屏幕像素"爬"，常见于远处高频纹理 |
| sub-pixel jitter（亚像素抖动） | 引擎/相机讨论 | 成因侧：内容位置有小于 1 像素的位移 |
| pixel wobble / pixel warp | 像素风美术 | 更宽泛，也包含"非整数缩放导致像素大小不均匀" |
| **temporal aliasing**（时间域走样） | 信号/图形学教材 | **最本质的归类**：走样发生在"时间方向"上（见 §6） |

最后一个是理解它的关键：它不是"画错了"，而是**采样定理在时间方向上的老问题**——画面在时间上被离散成"帧"，内容在空间上被离散成"像素"，当内容以低于 1 像素/帧 的速度移动时，两次采样之间的差异所携带的信息（0.3 像素的位移）无法被表达，只能被量化成"动"或"不动"，于是就出现了一格一格的跳。

## 3. 机制：为什么"像素是点"是理解一切的钥匙

很多人对"像素"的直觉是"一个方块"，于是会推不出这个问题。官方文档把这件事说得很直白：

- Microsoft 的 D3D9 文档里，屏幕空间的 `(0, 0)` **就是左上角那个像素的中心**，显示器的左上角在 `(-0.5, -0.5)`；
  并且**像素在硬件上被当作"点"而不是"格子"**（文档里专门画了"pixels modeled as squares"和"pixels are dots"两张图对比）［A2］。
- D3D11 的光栅化规则同样以**像素中心**为判据："任何落在三角形内部的像素中心会被绘制"（外加 top-left 规则处理边界归属）［A1］。

所以渲染管线里真正发生的事情是：

```
对屏幕上每个像素，取它的中心点 → 反算这个点落在纹理的哪里 → 在那个位置采样纹理 → 得到颜色
```

像素是"采样点"，纹理（纹素）也是"采样点网格"。**问题永远出在这两套采样点的相对位置上**：

- 两套网格**对齐**（每个屏幕像素的中心恰好落在某个纹素的正中心）→ 采样稳定，画面"逐像素复刻"，不会跳；
- 两套网格**错开半个像素**→ 采样点落在**四个纹素的交界角**上。这时：
  - 用双线性过滤：四个纹素被平均 → 画面发糊（这是 D3D9 时代"半像素"问题的经典表现）；
  - 用最近邻（POINT，像素风常用）：取的是"离得最近的那一个"，而**什么叫"最近"在边界上是模糊的** → 内容平移一点点，采样就会从纹素 n 翻到 n+1 → **跳变**。

最后这一条就是本问题的全部机制，一句话：**最近邻采样是"阶梯函数"，而内容位置是连续的，阶梯的台阶宽度是 1 像素**。

顺带说清"半像素"这个词的三处不同来源，它们经常被混着讲：

| 说法 | 说的是什么 | 出处 |
| --- | --- | --- |
| "顶点要减 0.5" | D3D9 的 API 约定：屏幕空间坐标是像素**中心**，所以四边形的边要减 0.5 才落在像素**边界**上 | ［A2］ |
| "纹素中心在 (i+0.5)/n" | 纹理侧的采样约定：文档用 4×4 纹理演示了"顶点 UV(0,0) 落在纹素角上"会采样错位 | ［A2］［A3］ |
| "相机吸附到 0.5 像素" | 我们讨论的**取整误差**：把相机取整到整数像素后，误差上界恰好是 0.5 个设备像素（见 §4） | 本工程 |

## 4. 数学：什么时候内容会落在像素边界上

设世界坐标 `world`、相机位置 `cam`、缩放 `zoom`（本工程只能取 1 或 2），那么内容在屏幕上的位置是：

$$
screen_x = (world - cam) \cdot zoom
$$

（忽略屏幕中心偏移，它是个常数，不影响对齐性。）

**要落在整数像素上**，就要求 `screen_x` 是整数。假设素材是按"1 世界单位 = 1 像素"画的（`world` 是整数格点），那么条件化简为：

$$
cam \cdot zoom \in \mathbb{Z}
\quad\Longleftrightarrow\quad
cam = \frac{n}{zoom},\ n \in \mathbb{Z}
$$

**这就是那句看起来有点怪的代码的来历**：

```c
cam = roundf(cam * zoom) / zoom;      // 先乘回"设备像素"再取整，最后换回世界长度
```

三个必须记住的点：

1. **吸附的量是"1 个设备像素"，不是"1 个世界像素"。** 直接写 `roundf(cam)` 在 `zoom = 2` 时只吸到半个设备像素，问题只解决一半。
2. **误差上界 = 0.5 个设备像素**（四舍五入的最大偏差）。在 `zoom = 1` 的 4K 屏上，0.5 设备像素 = 屏高的 0.006%；这就是"代价几乎为零"的量化依据。
3. **`round` 与 `floor` 都行**，只是误差方向与大小略不同（`floor` 的误差是 0~1 像素，`round` 是 ±0.5 像素）。选 `round` 更精确；老游戏里用 `floor` 的多，因为当年整数运算更便宜。

**为什么"相机取整"和"每个物体取整"效果一样**：`(world - cam) * zoom` 里 `world * zoom` 已是整数，所以只要 `cam * zoom` 是整数，**所有**整数格点上的内容就都对上了。因此"吸相机"是**一次操作解决整幅画面**的办法——这也是它成为主流做法的原因。

**尾巴有多长**（为什么抖动总是集中在最后一段）：指数收敛下每帧位移 = `k × 当前滞距`，本工程 `k = 1 - e^{-9/60} ≈ 13.9%`。当滞距 < 1 像素 / 0.139 ≈ 7.2 像素时，每帧位移就小于 1 个设备像素，全部落在"抖动区间"里；从 7.2 像素收敛到吸附阈值大约十几帧（本工程实测 15~19 帧，见 `docs/camera.md` §4.2）。**只要相机还在做亚像素位移，抖动就在**——这就是"光调整吸附阈值治不了本"的原因。

## 5. 来源之一：这个问题的历史脉络

> 这一节是**时间线叙事**，其中只有标了 `［A…］` 的断点有文档支撑，其余是行业惯例性的概括（末节 B 档）。我不做逐机型考证。

**① 1980s–1990s：这个问题在硬件层面不存在。**
那个年代的 2D 硬件（PPU / 位图图层 / 精灵表）基本只在**整数像素**上放置精灵与滚动背景——硬件根本没有"0.5 像素"这种概念。所谓"平滑移动"是软件做出来的：内部用一个小数速度累加器，每帧累加到整数才真正绘制。"亚像素精度"只是**逻辑**精度，屏幕上没人见过半像素。（具体机型各有技巧与例外，这里只做整体概括。）

**② 1996–2005：PC 2D 时代（DirectDraw / GDI / blit）。**
合成与 blit 同样是整数像素，问题表现为朴素的"位置取整"——角色移动看起来一格一格，但**不会抖**，因为画面里的东西要么整体挪 1 像素，要么不动。

**③ 2000–2010：D3D9 时代，2D 被"画成三角形"。**
3D 管线把 2D 也变成"带纹理的四边形 + 浮点顶点坐标"，于是**内容位置第一次可以取小数**。同时期最有名的一类坑就是"半像素偏移"：D3D9 的屏幕空间以像素**中心**为原点，顶点需要减 0.5 才能把纹素正确盖在像素上；OpenGL 的约定不同，所以"同一份 2D 代码在两个 API 下看起来差半个像素"成了当年的经典症状［A2］［A3］。（当年大家把 2D 三角形化视为临时方案，抖动被认为是"过渡期代价"。）

**④ 2008 之后：显示从 CRT 转向液晶，像素风从"限制"变成"审美"。**
显示器不再有 CRT 的扫描模糊与光晕来"抹平"1 像素的差别，画面第一次被完整、逐像素地呈现。与此同时独立游戏复兴了像素风——**像素画变成一种主动选择的美学**，于是"维持 1 世界像素 = 整数个屏幕像素"从"硬件自动做到的事"变成"必须人为保证的工程约束"。抖动问题正式变成一类工程问题。
（这个转折本身没有单一权威出处，是行业叙事；能佐证它的是下一阶段：引擎开始为它提供专门功能。）

**⑤ 2013–2020：引擎把解法产品化。**

- Unity 的 **2D Pixel Perfect** 包里，`Pixel Snapping`、`Upscale Render Texture`、`Reference Resolution`、`Crop Frame` 是四个互相独立、可组合的开关［A4］；
- Godot 提供引擎级的 `snap_2d_transforms_to_pixel` / `snap_2d_vertices_to_pixel`，以及"基准分辨率 + 整数倍缩放"的整套投影设置［A5］［A6］。

**⑥ 2015 之后：高分辨率 + 高刷新率把这问题两头都放大了。**

- 空间侧：1440p/4K 让 1 像素细节更容易被看清（绝对尺寸变小了，但**对比度不变**）；
- 时间侧：逻辑固定 60Hz 而显示器 144Hz 时，渲染插值出的位置每帧都不同，"亚像素位移"的帧数变多——抖动出现的**机会**变多。
  （本工程就是"60Hz 逻辑 + 渲染插值 + 平滑相机"这套结构；这一条是我的推断，我们没有单独测过刷新率对它的影响。）

## 6. 三个容易混为一谈的"抖"

排错时先把症状分对，不然会改错地方：

| | 触发条件 | 本质 | 典型解法 |
| --- | --- | --- | --- |
| **亚像素抖动**（本文） | 相机/内容**在动**，且每帧位移 < 1 像素 | **空间**采样错位（内容落在两套采样点网格之间） | 整数吸附 / 整数倍缩放 / 低分辨率离屏再放大（§7） |
| **非整数缩放** | 缩放倍率不是整数（例如 1366/640 = 2.133） | **空间**：源像素被不均匀地放大 | 只允许整数倍缩放 + 黑边［A5］ |
| **judder / stutter** | 帧率与显示器刷新率不匹配、或帧时间不稳 | **时间**采样：帧与帧之间的时间间隔不均 | 固定步长 + 渲染插值（`alpha`）［A7］ |

判断技巧（我的归纳）：**相机完全静止之后还抖吗？**

- 静止就不抖、只随相机移动抖 → 前两种（看内容是否只有 1 像素宽：是则前者，整幅都在变则后者）；
- 静止也在抖 → 多半是动画本身、或者帧节奏问题，不是本文这个。

> 3D 里还有一条**完全不同**的路线：TAA——逐帧抖动投影矩阵再靠历史累积平均掉锯齿。它是"故意制造亚像素抖动再用时间平均消掉"，与 2D 像素风要的"稳定清晰的像素块"目标相反，别照搬。（TAA 的做法属于通用常识，未逐条核对。）

## 7. 解法清单

按"改哪一层"排列，每条都给出代价与代表实现。**注意最后两行是"治不了"的**——它们经常被误当成解药。

| 改哪一层 | 做法 | 代价 | 代表实现 / 出处 |
| --- | --- | --- | --- |
| **渲染期的变换** | 把相机（或每个绘制项）**吸附到整数设备像素** | 运动被量化成 1 像素台阶 | 本工程 `docs/camera.md`；Unity `Pixel Snapping`：在**渲染时**把 Sprite Renderer 吸到世界网格上，"防止亚像素移动"，并且**不改动 Transform 位置**［A4］；Godot `snap_2d_transforms_to_pixel` / `snap_2d_vertices_to_pixel`［A6］ |
| **视觉分辨率** | 先渲到接近参考分辨率的**离屏纹理**，再整数放大到全屏 | 整幅内容都被量化；通常要配整数缩放/黑边 | Unity `Upscale Render Texture`（"结果是未走样、未旋转的像素"）［A4］；Godot `stretch mode = viewport`［A5］ |
| **输出缩放** | 只允许**整数倍**缩放，不够就加黑边 | 屏幕边缘留黑；UI 也得跟着缩 | Godot `Stretch Scale Mode = integer`：官方给的例子是 640×360 基准在 1366×768 上，2.133× 会导致"像素缩放不均"、棋盘格"看起来不匀"，2× 才正确［A5］；Unity `Crop Frame`［A4］ |
| **采样方式** | 改用双线性/各向异性过滤 | 亚像素位移被"抹平"了，但像素画也糊了（不再是像素风） | 双线性过滤会平均 4 个纹素［A2］；D3D9 里 -0.5 偏移的本意就是"让采样点落回纹素中心"［A2］［A3］ |
| **美术方向** | 承认"1 像素 ≠ 1 屏幕像素"，直接按高分辨率画素材 | 失去像素风（对像素风游戏等于换风格） | Godot 给"非像素风桌面游戏"的建议就是高基准分辨率 + `canvas_items`［A5］ |
| **时序** | 固定步长 + 渲染插值 | **与像素对齐正交**：它治的是 judder | Gaffer On Games《Fix Your Timestep!》［A7］ |
| ❌ **抗锯齿** | MSAA / SMAA / FXAA | **治不了这一类**：MSAA 消除的是几何边缘走样，官方原文明确写着它 "does not reduce surface aliasing"（不减少表面/纹理走样）［A1］ | — |
| ❌ **只调吸附阈值** | 让相机"早点停" | 只能把亚像素尾段缩短（本工程实测 19→15 帧），**不能消除抖动**——那十几帧里相机仍在做亚像素位移 | 本工程实测，见 `docs/camera.md` §4.4 |

补充一个实践中很常见的折中（我的归纳，本工程用的是它的简化形式）：**只在慢速时吸附**——每帧位移 ≥ 1 像素时不吸（1 像素误差在快速移动中不可见），< 1 像素时才吸。这样既消除了尾段抖动，又不牺牲大幅慢速运镜的平滑性。本工程用了更简单的形式：常数阈值吸附 + 渲染期整数吸附，两者的组合等价于"亚像素位移一律不产生可见位移"。

## 8. 工程细节与常见坑

1. **吸附量必须按设备像素算**（`round(cam * zoom) / zoom`）。按世界像素算，在 `zoom = 2` 时只解决一半（§4）。
2. **只吸附"渲染用"的那份状态**，逻辑状态保持小数。这一条有三重好处：物理/确定性不受影响、回放与对拍不受影响、将来改渲染策略不用动逻辑。Unity 的 `Pixel Snapping` 也是**渲染时**吸附且明确**不改 Transform**［A4］——同一个思想。本工程把这份区分落在"逻辑相机 ↔ 渲染相机"两个变量上（`docs/camera.md` §1）。
3. **吸附粒度**：只吸相机（一次解决整幅画面，但角色自身仍在亚像素位置）vs 吸所有绘制项（更"纯"，但所有运动的平滑性都被量化）。本工程选了前者，并明确记录了残留（`docs/camera.md` §4.6）。
4. **整数缩放与像素对齐是配套的**：如果缩放倍率非整数，即使相机取整，纹素与像素也不再 1:1——画面上会出现"有些源像素占 2 个屏幕像素、有些占 3 个"，棋盘格看起来不均匀［A5］。像素风游戏通常只允许整数倍缩放，就是这个原因。
5. **全屏模式本身可能吃掉一个像素**：Godot 文档提醒，Windows 上普通的 `Fullscreen`（为支持逐像素透明而保留 1 像素行）会让屏幕高度比独占全屏少 1 像素，于是整数缩放会选到**更小的倍率**；他们建议用 `Exclusive Fullscreen`［A5］。这类"差 1 像素"的细节是整数缩放的经典坑。
6. **别把三种"半像素"搞混**（§3 的表）：API 约定（顶点 -0.5）、纹理采样（纹素中心 vs 角）、取整误差（±0.5 像素），改错一个地方会越修越乱。
7. **吸附阈值也要按设备像素定义**，否则它的语义会随缩放漂移（本工程踩过：同一个数在 `zoom = 1` 与 `zoom = 2` 下含义不同）。

## 9. 怎么自己诊断

**① 定点复现（最省事的自测）**：造一张 1 像素竖线或棋盘格，让相机以 0.1 像素/帧匀速平移，盯住同一列像素，看颜色是否在相邻两格之间跳。有跳 → 就是本文的问题。

**② 三问定位法**（§6）：只在相机移动时抖？只有 1 像素宽的东西抖？相机静止后抖不抖？

**③ 用轨迹文件对拍（本工程用的办法）**：改代码前后，跑**同一个**输入脚本、各输出一份 `--trace`，逐行比较相机列。
- 只改"渲染期吸附"时，相机列**应当逐行完全不变**（因为逻辑相机不经过它）；
- 改"吸附阈值"这类逻辑侧参数时，相机列会变，但角色状态列（`x / y / vy / state`）必须一行都不变。
- 坑：相机列与**视口尺寸**强相关（夹取范围随窗口变），两边必须用同一个 `--window`；**全屏时如果关卡整幅都在视野里，相机会被永远夹在关卡中心，根本不会动**——本工程就这么白跑过两条轨迹。

**④ 别忘了先排除"内容本来就在动"**：角色、粒子的自身位置也是小数，它们自己的细节也会跳（本工程未对其取整），这属于"运动物体自身的亚像素抖动"，与相机取整是两件事。

## 10. 本工程选了哪条路

- **主解**：渲染期把**渲染相机**吸附到整数设备像素（只吸渲染那份，逻辑相机保持小数）；
- **补充**：吸附阈值按**设备像素**定义，让相机精确停在目标上（实测把亚像素尾段从 19 帧缩到 15 帧）；
- **不做**：不给角色/粒子逐项吸附（会量化所有运动的平滑性）；不改用双线性过滤（会毁掉像素风）；不引入离屏低分辨率渲染（本工程分辨率与缩放是 1:1 / 2:1，没必要多一层）。
- 具体代码、四条不变量、实测数据见 `docs/camera.md`。
