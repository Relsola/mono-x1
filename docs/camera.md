# 相机系统（平滑跟随 · 边界夹取 · 像素对齐）

涉及文件：`include/camera.h`、`src/camera.cc`、`src/game.cc`（驱动相机）、`src/main.cc`（渲染相机）、
`src/d3d12_renderer.cc`（消费相机）、`include/debug/trace.h`（`cam_x` / `cam_y` / `zoom` 列）、`include/game.h`（快照里的相机）。

> 本篇只讲**本工程的实现与不变量**。想先搞清楚这个问题本身的来龙去脉、业界各种解法（含历史与资料来源），
> 看 `docs/pixel-jitter.md`。

## 1. 数据流：逻辑相机只按固定步长更新

```
固定逻辑步（game.cc）
  camera_profile_for()  → 只选出档位名（不写数值）
  camera_follow(&game_state.camera, 角色位置, 关卡边界, 视口像素, FIXED_TIMESTEP, 档位)
    ├─（档位要求时）竖直死区：目标在窗口内就保持相机不动
    ├─ 目标点按关卡边界夹取（关卡比视野小的那个轴 → 直接对齐关卡中心）
    └─ 向目标指数收敛 + 贴近吸附
  → game_state.camera   进 GameStateSnapshot / 回放 / trace

每渲染帧（main.cc）
  在 prev_camera → camera 之间按 alpha 插值（让 60Hz 逻辑在高刷屏上平滑）
  → **吸附到整数设备像素**（只吸这份渲染相机）
  → renderer_frame_begin(camera_x, camera_y, zoom, ...)

d3d12_renderer.cc
  内容位置 = (世界 - 相机) * zoom，精灵走 POINT（最近邻）采样
```

## 2. 三层结构（与输入层的「动作表」同一种思路）

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 意图词汇表 | `camera.h` 的 `CameraProfile` + `camera_profile_name()` | 有哪些档位、日志与 `--camera` 怎么叫 |
| 数值 | `camera.cc` 的 `CAMERA_PROFILES[]` | **全项目相机数值的唯一来源** |
| 选择点 | `game.cc` 的 `camera_profile_for()` | 什么场景用哪档（只看固定步长数据，只选名字不写数值） |

| 字段 | 单位 | 含义 |
| --- | --- | --- |
| `rate_x` / `rate_y` | 1/s | 收敛速度：每帧走掉 `1 - e^(-rate*dt)`（9 ≈ 0.25s 走完 90%）；稳态滞距 ≈ 速度 / rate |
| `deadzone_y` | 像素 | 竖直死区半高；0 = 完全跟随 |
| `snap_pixels` | **设备像素** | 差距小于它就一次到位。按设备像素定义，用时除以 `zoom` |

- 加一档 = `CameraProfile` 加一项 + 表加一行 + `camera_profile_name` 加一个 case + 选择点加分支。
  不要提前加没人用的空档位。
- 档位是**策略**（跨帧不变、由场景决定）→ **不进快照**；进快照的只有跨帧会变的相机**位置**。

## 3. 四条不变量

1. **不露出关卡外**：夹取作用在**目标点**上、且发生在插值之前，插值两端（上一帧相机位置、夹取后的目标）都在界内
   → 结果必在界内。关卡比视野小/矮的轴直接对齐关卡中心。（`game_init_asset` 以 `dt = 0` 贴合一次，
   所以初始化那一帧也满足这条。）
2. **角色速度归零 → 相机动量归零**：指数收敛只能无限接近，所以有 `snap_pixels` 吸附；否则相机永远以极小速度微动。
3. **传送由调用方告知**：判据是「角色这一帧实际走了多远」（`game.cc` 的 `CAMERA_TELEPORT_MARGIN`），
   **不能**用「相机离目标多远」—— 后者混着跟随滞距（跑动 ≈ v/rate ≈ 71px、满速下落 ≈ 178px），
   会让相机在正常跑动/跳跃时周期性瞬移。
4. **确定性**：相机只按固定步长的数据更新；渲染期的插值与吸附都不写回逻辑状态（见 §4.3）。

普通地图连接也遵循第 3 条的边界：角色的碰撞盒完全通过门洞后，`game.cc` 会换到已预载的目标世界，
并以 `dt = 0` 把相机立刻夹到新世界入口；随后角色按基础速度自动走到入口落点，相机恢复固定步长跟随。
这不是传送动画：它只处理普通房间连接，过渡期锁定控制且无敌，也给后续目标世界资源初始化留出预算。
真正的传送将另有快速加载动画和预设落点，不能复用“正在穿门”的状态。

## 4. 专题：亚像素抖动（pixel shimmer）

### 4.1 现象

4K 全屏、画面里有 1px 细线（砖缝、线框）时最明显：相机跟随收敛的**最后一小段时间**里画面在"疯狂细微抖动"，
像整幅画面在颤；一旦相机完全静止，抖动就消失。用 `--window` 缩小窗口后明显变轻。

### 4.2 根因（两句话）

1. **内容位置是小数、而采样是最近邻**：`(世界 - 相机) * zoom` 里的相机带小数，同一个纹素在两帧里可能落在
   **相邻的目标像素**上 → 1px 宽的细节在"亮/灭"之间跳（线条越细比例越大：1px 线就是 100%；大色块看不出来）。
   4K 只是让它更容易被看见。
2. **指数收敛的尾段恰好全是亚像素位移**：`rate = 9` → 每帧走掉 13.9% 的滞距，滞距掉到 7.2px 以下后每帧位移
   就小于 1 个设备像素，全部落进第 1 条的触发区间。**实测最长连续"亚像素尾段" 15 帧（≈0.25s）**，
   修改前 19 帧（≈0.32s）—— 这就是抖动为什么集中在跟随的最后一小段，而不是整段跟随过程。

> 机制细节（含"像素是采样点"的模型、对齐条件 `cam × zoom ∈ Z` 的推导）、历史脉络与其他解法，
> 见 `docs/pixel-jitter.md` §3–4 与 §7（那里有完整推导和逐条资料来源）。

### 4.3 解法一（主解）：渲染期把相机吸附到整数设备像素

```c
// main.cc：紧跟 render_camera 的三行插值之后
f32 render_zoom = render_camera.zoom;
render_camera.pos_x = roundf(render_camera.pos_x * render_zoom) / render_zoom;
render_camera.pos_y = roundf(render_camera.pos_y * render_zoom) / render_zoom;
```

- **为什么是 `round(cam * zoom) / zoom`**：要让整数世界坐标落在整数设备像素上，等价于要求 `cam * zoom` 是整数；
  除以 `zoom` 只是换回世界长度。**吸附量是 1 个设备像素，不是 1 个世界像素** —— 否则 `zoom = 2` 时只吸到半个像素。
- **为什么只吸"渲染相机"**：`render_camera` 是 `main.cc` 里插值出来的**局部变量**，只喂给 `renderer_frame_begin`；
  逻辑相机（进快照 / 回放 / trace 的那份）保持小数 → 确定性、断言、轨迹对拍全不受影响。
  这是代码结构上的保证，不是"对拍没测出差异"。（本轮 A/B 的两条轨迹都带着这个吸附，所以拿它证明不了这一点。）
- **代价**：相机的屏幕位置被量化成 1 个设备像素的台阶。跑动时约 10.7px/帧，台阶被速度掩盖；
  4K 下 1 个设备像素 = 屏高的 0.05%。

### 4.4 解法二（补充）：吸附阈值按设备像素定义

`snap_pixels` 从「0.5 世界像素」改成「1.0 **设备像素**」（用时除以 `zoom`）：

1. **语义不再随缩放漂移**：旧写法在 `zoom = 2` 时等于 1 个设备像素、`zoom = 1` 时等于 0.5 个，同一个数值两个含义；
2. **与解法一配套**：不足 1 个设备像素的差距，渲染出来完全一样，再慢慢挪只会拖长"看着不动"的尾段；
3. 相机最终**精确停在目标上**（而不是停在某个半像素偏移处）。

实测（同一套 43 条断言脚本，`--window 1280x720`，1241 个逻辑步）：

| 指标 | `snap_pixels` = 0.5 | `snap_pixels` = 1.0 |
| --- | --- | --- |
| 相机在动的帧 | 938 | 902 |
| 其中**亚像素位移**帧（0 < \|Δ\| < 1px） | 220 | 184（−16%） |
| 最长连续亚像素尾段 | 19 帧 | 15 帧 |
| 逻辑状态列差异（x / y / vy / state） | — | **0** |
| 相机列差异 | — | 318 帧 |

**分工要说清**：解法二只把尾段缩短约 1/5，**它并不能消除抖动** —— 那 15 帧里相机仍在做亚像素位移。
让抖动"消失"的是解法一（亚像素位移在屏幕上被量化成"不动"）。两者是「看不见」与「真的停下」的关系。

### 4.5 为什么像素风既放大它、又让它好解决

**放大（为什么本工程比多数 3D 游戏更在意）**

- POINT 采样不做插值，0.5px 的错位**没有**被模糊掩盖，直接表现为整格跳变；
- 像素风美术全是"1 世界像素 = 1 设备像素"的硬边细节（细线、描边、砖缝都只有 1px 宽），
  抖动的相对幅度是 100%。

**好解决（为什么整数吸附在这里的代价≈0）**

- 风格本身就是**离散**的：把相机吸附到整数像素不引入视觉误差（位置偏差 ≤ 0.5 个设备像素），
  "运动被量化成 1px 台阶"本来就是像素画的呈现方式。换成高清/矢量风格，细节密度远高于 1 像素，
  整数吸附会变成肉眼可见的跳动 —— 那类风格通常宁可双线性过滤 + 亚像素移动。
- 缩放是**整数倍**（本工程只有 1 / 2 两档）："1 世界像素 = 整数个设备像素"这个前提成立，取整才能真的对齐。
  一旦允许非整数缩放（1.5× 之类），纹素与像素不再 1:1，即使相机取整也会出现像素大小不均匀
  —— 这也是像素风游戏通常只允许整数倍缩放的原因。
- 4K 让代价进一步趋近于零：1 个设备像素 = 2160 行里的 1 行。

### 4.6 已知残留与边界（本次刻意没做）

- **角色、粒子自身的亚像素位置没被吸附**：它们自己的细节仍会随移动轻微跳，但移动幅度远大于 1px，看不出来。
  要严格 pixel-perfect 就得对所有绘制项吸附，代价是把运动的平滑性也一起量化 —— 现在不做。
- 按住 Q 放大的那一帧，`zoom` 会在 1↔2 之间插值出小数 → "1 个设备像素"短暂漂移（只一帧）。
- 将来若做过场那种**慢速大幅度运镜**，1px 台阶会变可见；那时的退路是"只在慢速时吸附"（加阈值），而不是取消吸附。

## 6. 怎么验证相机改动

- **手感**：`--camera default` 与 `--camera precise` 各跑一遍回归（43 条断言应全过），再目视对比。
- **像素对齐**：窗口化（`--window 1280x720`）与全屏各看一次，重点看 1px 细线在**相机收敛尾段**是否还在跳。
- **有没有污染逻辑**：只改渲染吸附时，`--trace` 的 `cam_x` / `cam_y` / `zoom` 应逐行不变
  （逻辑相机不经过渲染吸附）；改 `snap_pixels` 时相机列会变，但 `x / y / vy / state` 必须逐行不变。
- **坑**：**全屏（3840x2160）时关卡整幅都在视野内**，相机被夹在关卡中心、永远不动 ——
  想看相机行为必须用 `--window` 让关卡大于视野。相机列还与视口尺寸强相关，对拍两边窗口必须一致。

## 7. 参考资料

> 这一节只列直接支撑本篇结论的几条；**更完整的资料整合（含历史脉络、业界其他解法与逐条可信度标注）在 `docs/pixel-jitter.md`**。

搜索关键词：pixel-perfect camera / integer camera snapping / sub-pixel jitter / texel crawl / pixel shimmer。

- Microsoft Learn《Directly Mapping Texels to Pixels (Direct3D 9)》
  <https://learn.microsoft.com/en-us/windows/win32/direct3d9/directly-mapping-texels-to-pixels>
  —— 像素是"点"不是"方块"、纹素与像素为什么要对齐（经典 -0.5 偏移的来历）。本文第一层根因讲的就是同一件事。
- Godot 4 `rendering/2d/snap/snap_2d_transforms_to_pixel`（同页还有 `snap_2d_vertices_to_pixel`）
  <https://docs.godotengine.org/en/stable/classes/class_projectsettings.html#class-projectsettings-property-rendering-2d-snap-snap-2d-transforms-to-pixel>
  —— 引擎级同款开关，官方明确写了它的取舍："更锐利，但运动更不平滑，**尤其在 Camera2D 平滑开启时**"
  （正是"平滑跟随 + 整数吸附"这套组合的代价，与本工程 §4.3 一致）。
- Godot 4 `Camera2D` <https://docs.godotengine.org/en/stable/classes/class_camera2d.html>
  —— `position_smoothing_enabled` / `position_smoothing_speed` 对应本工程的平滑跟随；
  `reset_smoothing()`（"立即把相机设到它当前的目标"）对应本工程的传送 `dt = 0` 与贴近吸附。
  该页也提醒：`Camera2D` 的节点位置不等于屏幕实际位置（平滑/边界会改变它）—— 与本工程"逻辑相机 vs 渲染相机"是同类区分。
- Gaffer On Games《Fix Your Timestep!》<https://gafferongames.com/post/fix_your_timestep/>
  —— 固定步长 + 渲染插值（`alpha`）。用来区分两种不同的"抖"：帧率不匹配造成的 judder（本文不涉及）
  与本文的亚像素抖动（采样落在像素边界上）。
